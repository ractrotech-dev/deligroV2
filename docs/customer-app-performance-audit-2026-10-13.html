A. Summary

Optimise the existing app. A Flutter rewrite is not justified by this evidence. Every customer tab switch is a server render: one round-trip to the server that costs about 0.45 to 0.7 s before the first byte, plus 0.5 to 2 s of download for the page data. Nothing is reused when the customer returns to a tab. The biggest single outlier is the Search tab, which sends about 1.05 MB of page data on every visit because it loads every restaurant with its full menu.
  • All numbers below are what a browser saw. The server's own render time is not separated out (no Server-Timing headers exist), so "wait" includes network latency.
  • None of the top fixes needs a new APK: the four Capacitor shells load the live site.

B. Method and limits

  • Browser: Playwright Chromium at a 390 x 844 phone viewport, no CPU or network throttling. A real mid-range phone on 4G will be slower than these figures.
  • Account: the demo admin account, used only to open the customer app (which accepts any signed-in user). It has no active order, so the Orders tab auto-refresh was not exercised. Prefetches of /admin, /manager and /profile/favorites on the Home tab come from admin-only links and would not occur for a normal customer.
  • Small samples: 1 to 2 runs per page, one location. Treat the figures as orders of magnitude, not benchmarks. In-page frame timing was discarded because this browser throttled animation frames to whole-second steps; the figures below come from the browser's resource timing for the page-data requests instead.
  • No credentials, tokens, phone numbers or request payloads are recorded here.

C3. Other requests seen

  • /api/banners took 1.65 s to respond when the Stores tab loaded.
  • /manifest.webmanifest is re-requested on every navigation (small, 0.3 KB, but a pointless round-trip).
  • The Stores tab prefetches three restaurant pages (about 6 KB each, 0.9 to 1.6 s each). Cheap, but it competes with the page the customer is actually waiting for.
  • No failed requests (4xx or 5xx) were seen in these runs. The console showed no errors.

E. Not measured

  • Server-side render time per page. This needs Server-Timing headers or logs, which do not exist yet.
  • Behaviour on a real mid-range Android phone over 4G, including WebView memory and dropped frames.
  • Orders tab auto-refresh while an order is active. The code refreshes every 10 s (REFRESH_MS = 10_000 in orders/page.tsx), and each refresh is a full server render.
  • The Rider, Vendor and Manager apps.

F. Flutter proof of concept?

Not now. The measured delays are server round-trips and oversized payloads. A Flutter app would call the same backend, so it would inherit all of them. Fixes 1, 2, 5 and 7 are small and should be done first. If the customer app still feels slow after fixes 1 to 8 on a real phone, rerun this audit; if scrolling or animation is still poor then, a one-screen Flutter proof of concept (the Home feed, using the environment already described in docs/FLUTTER_SETUP.md) becomes a reasonable experiment.
