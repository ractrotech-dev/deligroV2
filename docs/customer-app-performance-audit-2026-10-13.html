A. Summary

Optimise the existing app. A Flutter rewrite is not justified by this evidence. Every customer tab switch is a server render: one round-trip to the server that costs about 0.45 to 0.7 s before the first byte, plus a download phase (0.5 to 2 s in the measuring browser, which received uncompressed data; see section G, so a real phone should see less). Nothing is reused when the customer returns to a tab. The biggest single outlier is the Search tab, which sends about 1.05 MB of decoded page data on every visit (about 80 KB gzipped on the wire) because it loads every restaurant with its full menu.
  • All numbers below are what a browser saw. The server's own render time is not separated out (no Server-Timing headers exist), so "wait" includes network latency.
  • None of the top fixes needs a new APK: the four Capacitor shells load the live site.

B. Method and limits

  • Browser: Playwright Chromium at a 390 x 844 phone viewport, no CPU or network throttling. Correction: this browser sent no Accept-Encoding header, so the server returned uncompressed data and every "KB", "Download" and "Page data" figure here is the decoded size. A real phone browser asks for Brotli or gzip, so its transfers are much smaller and its download phase shorter. A real mid-range phone will still be slower on CPU (parsing and rendering) than this machine.
  • Account: the demo admin account, used only to open the customer app (which accepts any signed-in user). It has no active order, so the Orders tab auto-refresh was not exercised. Prefetches of /admin, /manager and /profile/favorites on the Home tab come from admin-only links and would not occur for a normal customer.
  • Small samples: 1 to 2 runs per page, one location. Treat the figures as orders of magnitude, not benchmarks. In-page frame timing was discarded because this browser throttled animation frames to whole-second steps; the figures below come from the browser's resource timing for the page-data requests instead.
  • No credentials, tokens, phone numbers or request payloads are recorded here.

G. Update: Search fix 1 (payload slimming)

What changed. The brief for fix 1 was "send restaurant summaries, load menus on open". That cannot work here: Search is dish-first (its default tab lists priced dishes with an Add button) and ranks over every dish on the client, so every menu is needed. The change is narrower: src/lib/search/slim-catalog.ts leaves out the menu-item keys that hold their default (discountPrice: null, soldOut / popular / bestseller when false, unitsSold: 0) before the catalog is sent to the browser. Only the Search page uses it, so Home and Stores are untouched. Every reader of those fields already treats "absent" as the default.

MeasureBefore (live, 5 runs, median)After (projected)
Search page data1,074.9 KB778.1 KB (27.6% smaller)
Tab switch, total2,473 ms (1,737 to 2,916)to be re-measured after deploy
Download phase1,960 msto be re-measured after deploy
Wait for first byte506 msunchanged by this fix

The "after" size is a projection made by removing exactly those keys from the real live payload (3,572 dishes across about 66 kitchens; 94 real popular and bestseller flags are kept). It is not a measurement of the deployed fix, so repeat the five-run measurement once this is live.

Verified: npm run test:search-payload (41 checks) runs the real ranking over the original and the slimmed catalog and requires identical results for queries, filters, sorting, effective price and sold-out state. The 80 existing ranking checks, type-check and lint pass.

Correction: the response is compressed. An earlier version of this section said the Search response goes out uncompressed. That was a measurement artifact: the measuring browser sent no Accept-Encoding header, so the server sent identity data. Checked afterwards: a public page's page data (text/x-component) comes back Content-Encoding: br (8,840 bytes become 2,675), a JS chunk comes back br, and the authenticated /search response comes back br when compression is requested. Compression is working; the content type is not the cause of anything.

What slimming really buys. Gzipping the live Search payload gives 81.3 KB before and 74.4 KB after slimming, about 8% less on the wire (Brotli will be somewhat smaller for both). Repeated keys such as "soldOut":false compress to almost nothing, so the 27.6% saving is in decoded size: less to parse, hold in memory and hydrate, which matters on a low-end phone, not on the download. The earlier 2.4 to 2.8 s Search switch time is therefore an overstatement of the download share. What remains true: every switch still costs the 0.45 to 0.7 s server round-trip, and a phone has to parse about 1 MB of data (about 780 KB after this fix).

Next measurement: time Search on a real Android phone, or with CPU throttling and a real Accept-Encoding, to see whether the cost is network or parsing. Until then the ranking of fixes 2, 3 and 5 (avoid the round-trip, trim the fixed server cost) is better supported than fix 1.

Larger options, not done (worth it only if a real phone shows parsing is the problem): (a) serve the catalog from a cacheable JSON endpoint that the browser keeps between visits (the data is public; the existing blanket no-store rule for /api would need a deliberate exception, like /api/app-version); (b) shorten the repeated image URLs, which are about 340 KB of the original payload.

  • The proxy's cost is the Supabase session check. session is within 1 ms of proxy on every response, and it is a steady 155 to 190 ms. The proxy does nothing else that takes time. That is roughly 35 to 40% of a tab's first-byte time, paid on every request, before any page work starts.
  • Every response came from iad1 (US East). The X-Vercel-Id on all measured responses reads bom1::iad1::…: the request enters at the Mumbai edge and is then served by a function in Washington. The repo has no vercel.json and no region setting, so the function region is whatever the Vercel project is set to (the Vercel default is iad1).
  • What that implies (inference, not yet proven). A session check taking about 160 ms from iad1 means the Supabase project is not near iad1. Every Supabase call a page makes pays that distance, and pages make several in sequence. This would also fit the 4 s admin dashboard and 5.5 s settlements page. The Supabase project's region has not been checked; it is shown in the Supabase dashboard under Project Settings, Infrastructure.
  • Outlier: one Orders request took 10.5 s to first byte (the other five were 443 to 700 ms). Not reproduced.
  • Search is not comparable with the older baseline. Section C measured about 0.5 s to first byte plus about 2 s of body; this run shows about 2.4 s to first byte and no body time, with the total unchanged at about 2.5 s. The response may now arrive in one piece. The reason has not been established, so do not use Search's TTFB for attribution; its total is the stable number.
  • The instrumentation itself did not slow anything: Stores and Orders first-byte times match the earlier baseline (456 to 478 ms).

Candidate fix (config, no code): run the Vercel functions in the region closest to the Supabase project (for a Mumbai project, bom1). If the two are in the same region, the session check should drop to a few milliseconds and each page query by a similar amount. Confirm the Supabase region first, change the Vercel project's Function Region (or add "regions" in vercel.json), then re-measure with this same header. Router reuse (staleTimes) remains a separate change.

F. Flutter proof of concept?

Not now. The measured delays are server round-trips and oversized payloads. A Flutter app would call the same backend, so it would inherit all of them. Fixes 1, 2, 5 and 7 are small and should be done first. If the customer app still feels slow after fixes 1 to 8 on a real phone, rerun this audit; if scrolling or animation is still poor then, a one-screen Flutter proof of concept (the Home feed, using the environment already described in docs/FLUTTER_SETUP.md) becomes a reasonable experiment.
