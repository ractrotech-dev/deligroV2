A. Summary

This is not decorative. A real, working location system already exists, so the right move is a few targeted fixes, not a new build. The header, the /location picker (GPS, Google Places search, saved addresses, map pin), the per-customer address table with row-level security, and a server-side delivery-area check at order time are all in place and wired together. Two real defects were found. (1) The chosen place is cached on the device and is not cleared at sign-out, so on a shared phone the next person sees the previous person's saved address in the header. (2) The header and checkout can name different places, because they read from two different sources.

C. Checklist, answered

Where does the header text come from?Real data (device place, else saved default address, else city default). Not hardcoded.

D. Defects (verified)

#DefectEvidenceSeverity
D1The picked place outlives the sign-out. Choosing a saved address stores its label, its full address line and its coordinates in localStorage. Sign-out is a plain form post whose landing page clears only service-worker caches and push registration; nothing removes deligro-loc-cache. On a shared phone the next person, including a guest, sees the previous person's address in the header and gets distances measured from their coordinates until they pick another place.src/components/pwa/pwa-provider.tsx (?signedout=1 handler), clearAppCaches in src/lib/pwa/service-worker.ts; the only code touching the key is location-store.tsMedium (privacy)
D2The header and checkout read different sources. The header prefers the device place (GPS or hand-picked) over the saved default; checkout always starts from the saved default. After a GPS fix the header says "Deliver to Nearby area" while checkout delivers to "Home". Checkout shows its own address and re-checks the area, so nothing is delivered to the wrong place, but the header can promise something checkout will not do, and card distances use a different origin from the order's eligibility check.home-header.tsx (shown = place ?? saved ?? fallback) against checkout-view.tsx (useSavedAddresses().selected)Medium (consistency)
D3The address API does not validate coordinates. lat and lng are stored as sent (any type or range). The delivery-area check at order time limits the damage, but bad rows can be saved.src/app/api/addresses/route.ts, [id]/route.tsLow

E. Design points to decide, and things I could not verify

  • Order coordinates come from the browser, not from the saved address. The server checks the submitted point against the radius (and refuses a missing one) but does not check that it matches the address text. A customer could send an in-area pin with an out-of-area line. The code states they are "checked, never trusted"; to go further, order creation would take an address id and read the row itself. A product call on how strict to be.
  • Map key restrictions. The key is public by design and must be restricted by HTTP referrer (and the Android shell's origin) in Google Cloud. I cannot see that from here.
  • Android runtime GPS. The manifest permissions are added, but the WebView's permission prompt and a real fix need a phone test.
  • Hindi. Hindi is switched off by the owner (HINDI_ENABLED = false in src/lib/i18n/lang.ts): the app renders English, and the Hindi strings in the code are dormant fallbacks. The location code follows the same flag.

F. Proposed plan (nothing implemented)

  1. Fix D1 (small, no product decision). On the ?signedout=1 landing, also remove deligro-loc-cache and reset the store to the city default. Consider caching only the locality and coordinates, not the full address line.
  2. Fix D2 (needs a decision). Option A: when a GPS fix or searched place is chosen, offer "Deliver here?" and save it as the default address, so header and checkout always agree. Option B: signed-in customers see the saved default in the header unless they explicitly chose another place this session, and checkout adopts that choice. Option A is the smaller change.
  3. Fix D3. Validate coordinates in the address API: finite numbers, latitude within ±90, longitude within ±180, both or neither.
  4. Optional (E, first point). Order creation by address id.
  5. Verify on a phone and in the cloud console (see the section above).

No new table, provider or state system is needed. A paid dependency is not introduced: Google Maps is already configured.
