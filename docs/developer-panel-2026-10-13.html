Deligro Developer panel

2026-10-13 · built in commits d7b1fc8, b519811, bddc13a and the account script · nothing is pushed or deployed yet.

What it is. A separate panel at /developer for how the app itself is doing and how it is configured, so the Admin console can be only the company's operations. It has its own role (developer), its own sign-in (/developer/login) and its own navigation. An account has one role, so a developer account is a separate login from any admin account. An admin cannot open the Developer panel, and a developer cannot open the admin console.

Release steps, in this order

The order matters: if the app is deployed before a developer account exists, nobody can open Observability until one does.

  1. Apply the database migration in the Supabase SQL editor. Run it alone, as one statement (Postgres will not let a new enum value be used in the transaction that adds it): 
    alter type public.user_role add value if not exists 'developer';
    This is the contents of supabase/migrations/0059_developer_role_enum.sql. It changes nothing else and the app keeps working without anyone using it.
  2. Create the developer account with a phone number that is not the one you use as admin. Try the dry run first: 
    npm run db:create-developer -- --phone 98XXXXXX01 --name "Your Name" --dry-run
npm run db:create-developer -- --phone 98XXXXXX01 --name "Your Name"
    The script refuses to turn an existing admin, manager, driver or vendor account into a developer (that would silently remove their access to their portal) unless you add --force. It uses the service-role key from .env.local, which points at the live project.
  3. Run the deployment audit (docs/DEPLOYMENT_AUDIT.md), then push. Pushing master deploys production.
  4. Check it: sign in at /developer/login with the developer phone (OTP). Open Overview and Observability. Then, in another browser, sign in as an admin and open /developer: you should be sent to the developer sign-in with an "access denied" notice.
  5. Rollback: redeploy the previous deployment. The enum value cannot be dropped, but an unused value is harmless.

Open decisions

  1. Platform configuration. It holds vendor commission, delivery fee and tax, order availability (the switch that pauses ordering), payments, dispatch, support and brand, and APK release versions. Moving all of it means admin staff can no longer change a fee or pause ordering. Options: leave it in Admin (recommended for the business settings); move everything; or move only the technical sections (payments, dispatch, alert sounds, app releases). Moving it also needs a second migration so the database lets the developer role write those settings; that is not written yet.
  2. Customer features. Which customer features should be switchable (for example online payment, promo codes, ratings, reorder, tipping)? Each needs the switch to hide it in the app and the server to refuse it, and the checkout ones need care.
  3. Storage. Kept in Admin. Say so if you want it moved.

Still to build in the panel

  • Database slow-query and connection visibility. The app cannot see these; the Supabase dashboard has them. The scorecard says so instead of inventing a figure.
  • Real-user performance from phones, and a migration-status check.
  • The monitoring jobs that are not scheduled (pg_cron: metrics rollup, alert evaluation, retention) and the alert rules that ship disabled. The Observability overview already reports these as "Not configured".
