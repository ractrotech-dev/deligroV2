A. Summary

Two of the three systems are largely built. Reviews already have verified-purchase rules, moderation, sub-ratings and a trigger that keeps each shop's average correct; what is thin is the customer-facing screen. Shop locations already require a map pin before a shop can go live. Delivery fee is the real gap: it is one flat amount (default ₹29, with an optional free-delivery threshold). There is no distance-based pricing, and distance is only used as a straight-line "do we deliver there" check. Anything beyond a flat fee is a new feature and needs a pricing decision from the owner first.

E. Recommendation (nothing implemented)

The project notes mark this phase as client handover with no new features, so only the small gaps below are candidates without a new owner decision. Distance-based fees are a new feature and need decisions first.

  1. Small, no pricing decision: add a customer-facing way to write feedback and sub-ratings after delivery (the database and API already support it), show recent review text on the restaurant page, and add a "report" button for customers.
  2. Small: add location_verified_at to shops and clear it when the pin changes, so an admin re-confirms it.
  3. Needs owner decisions before any code: a distance-based customer fee.
    • The rule: the base fee and the distance it covers, the extra rate per km, whether partial kilometres round up, and any cap.
    • Straight-line or road distance. Road distance needs a routing provider. Google Maps is already configured, but its routing API is separate, must be enabled, and is billed per request. For one small town, straight-line distance with a fixed factor, or a cached shop-to-address distance, may be accurate enough at no cost.
    • Whether free-delivery thresholds still apply on long trips.
    If approved, the build is: shop and customer pins, distance, a server-computed fee, the fee and distance stored on the order, and a re-check at checkout.
  4. Out of scope: rider pay.
