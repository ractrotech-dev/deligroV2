Posture

The authorization design is strong and applied consistently:

  • Every route and server action checks the caller before touching data: all 102 manager routes, 39 rider routes and 40 vendor routes, and every admin and developer server action.
  • ops_* RPCs are callable by the service role only, and each re-checks the actor.
  • Storage paths are built on the server.
  • Payments are verified by signature and settled through conditional state transitions.

The three confirmed defects share one root cause: a write a signed-in user can make straight to the database through PostgREST, where the database check is weaker than the app check. The app's own data layer writes with the user's session, so users can reach those same doors themselves.

Medium Direct order insert skips delivery fee, tax and order rules

The insert policy orders — customer insert lets any customer insert an order row. The insert trigger force_order_total_pending resets the total, discount and status, but not delivery_fee or tax_amount; the only constraint on those is ≥ 0. recompute_order_total then adds whatever the client sent. The platform pause, minimum order, delivery-area check and COD rules exist only in createOrder().

Trace
  • 0040_operator_can_order.sql:55: the insert policy
  • 0053_release_hardening.sql:70: the insert trigger
  • 0146_manager_products.sql:422: item prices are re-derived correctly, but only per item
  • 0053_release_hardening.sql:189: the total is computed from the client's values
Example
A ₹200 dish with a ₹30 fee and 5% tax should total ₹240. A direct insert gives ₹200.
Known?
The fee/tax part is the repo's own open item N-1 (docs/SECURITY_AUDIT.md:170). This audit confirms it is still open and widens it: the same door also bypasses the pause, minimum order, delivery area and COD rules.
Fix
Take the route N-1 already plans: put order creation behind a place_order() SECURITY DEFINER RPC and revoke direct customer INSERT on orders and order_items. As a stopgap, zero the fee and tax at insert and derive them in recompute_order_total.

Low Vendor can delete platform-funded coupons

The Partner-app API refuses this because owned() requires fundedBy === "vendor". The web portal's server action instead uses ownedCode(), which checks only the shop. Its delete then runs under the vendor's session, and the RLS delete policy, unlike the insert and update policies, has no funded_by condition.

Where
src/app/vendor/promotions/actions.ts:81, supabase/migrations/0041_vendor_coupons.sql:198
Fix
  • Add && existing.fundedBy === "vendor" to ownedCode().
  • Add funded_by = 'vendor' to the coupons — vendor delete USING clause.

Low ops_address_note is writable by vendors and customers

Migration 0142 says the column is "written only by ops_correct_order()". However, it never added the column to guard_order_update's locked list, and nothing clears it on insert. A vendor can PATCH their own shop's orders, and a customer can set it when inserting their own order. The rider's job card then shows the text as "Note from Deligro".

Lead Anonymous telemetry can push attacker-chosen text to every developer

POST /api/obs/client needs no session and always records at level error. Every distinct message becomes a new issue. Trigger 0170 queues a "new error" alert for each one, and sendIssueAlerts() pushes the title (the attacker's text, up to 180 characters) to every developer. The only limit is 30 per 5 minutes per clientIp().

Blocked on
  • Whether the deployment has VERCEL_ENV=production
  • Whether OneSignal is configured with a subscribed developer
  • Whether 0169/0170 are applied
  • Whether Vercel overwrites X-Forwarded-For
Owner check
Does the production developer console show "New error" alerts for anonymous client_error issues?
Likely fix
Don't queue alerts for kind='client' issues that have no actor, and add a global hourly cap in obs_take_alerts.

Hardening worth doing

None of these is a finding.

  • One SMS OTP signs into any role, admin included. MFA was removed in 0033, so a SIM swap on an admin's number gives full admin. Consider refusing OTP sign-in for operator roles, or restoring a second factor for them.
  • Vendors can read the full profile of every customer who has ever ordered from them. The policy is profiles — vendor reads order customers (0008), and the row includes phone, wallet balance, account status and push ID. 0162 removed this same read for managers.
  • Restaurant bank and UPI fields can be written through PostgREST. They are not in lock_restaurant_privileged_fields, so a hijacked vendor session could redirect payouts.
  • Write protection on orders, profiles and restaurants relies on hand-kept locked lists inside triggers. The ops_address_note finding is what happens when one is missed. Revoke table-level INSERT/UPDATE and grant per column, as 0058 already did for SELECT.
  • clientIp() trusts the first X-Forwarded-For hop. Every anonymous per-IP limit depends on how the edge treats that header.
  • Smaller items:
    • OTP consumption is not compare-and-set.
    • Manager cursor decoders use Date.parse only.
    • getPipelineHealth has no role check.
    • CSV export doesn't guard against leading tab or CR characters.
    • A feature-flag read error keeps serving the stale cache indefinitely.
    • orders.tip has no upper bound in the database.
    • CSP still allows 'unsafe-inline'.

What held up

  • Order data:
    • Column-level SELECT on orders (0058).
    • Item prices are re-derived in the database.
    • Coupons are applied under a lock, once per order.
  • Database RPCs:
    • Every ops_* RPC is service-role only and checks the actor.
    • No ungated SECURITY DEFINER function returns more than the caller's own data.
  • Payments and money:
    • The Razorpay webhook verifies HMAC over the raw body and fails closed without a secret.
    • settlePayment never moves a payment backwards.
    • Payouts require a second person to approve them, and the amount is recomputed at approval.
  • Sign-in: OTPs are hashed with scrypt and a pepper, compared in constant time, and each attempt is claimed before the comparison.
  • Redirects: safeNextPath blocks open redirects.
  • Uploads: file types are checked by their leading bytes, and storage paths are built on the server.
  • Failure modes: demo mode cannot run in production, and missing secrets close access rather than open it.
