Findings outside the checklist

  • Vendors see zero refunds. vendor-earnings.ts reads refunds with the vendor's own client, but row security only lets customers and admins read it, so the vendor earnings figure always shows 0 refunds — on the website today too.
  • The vendor portal has almost no API. It runs on Next.js Server Actions; only four vendor /api routes exist. A native app needs new routes for anything that sends pushes, dispatches riders, queues refunds or reads settlements.
  • Hindi is switched off by owner decision (3 October, HINDI_ENABLED = false) for every surface except the customer app. The document asks for Hindi labels where feasible.
  • No update gate for vendors. /api/app-version has release tracks only for rider and customer.
  • Status flow differs from the mockup. The database has placed → kitchen → ready → on_the_way → delivered; Accepted and Preparing are the same step.
  • Migration 0060 is pending approval and unapplied; new tables follow it as 0061 onward.

What this means for the build

About half of the vendor app can be built on existing data and rules. The rest needs server work first: vendor read access to settlements and refunds, a vendor API layer, and four new modules (marketing requests, support tickets, invoices, in-app notifications), each with an admin side to answer it. The phased plan is in docs/superpowers/specs/2026-10-21-vendor-app-design.md.

New migrations are validated in an in-process Postgres before review. Applying them to the live database and deploying the website remain the owner's steps.
