Deployment checklist

Do these in order. Each step is safe on its own: the website checks which migrations exist and falls back, and the app shows "This needs a Deligro update that isn't live yet" for a feature whose migration isn't applied.

  1. Apply the migrations, staging first if you have one, then production In the Supabase SQL editor, run each file whole, in this order: supabase/migrations/0062_store_inventory_options.sql → 0063_order_invoices.sql → 0064_growth_support.sql. 0061 is already live. I confirmed it today by probing order_status_events. Then run this check. Every column should come back true: 
    select
  to_regclass('public.store_holidays')      is not null as m0062_holidays,
  to_regclass('public.menu_item_variants')  is not null as m0062_variants,
  to_regclass('public.menu_item_addons')    is not null as m0062_addons,
  exists (select 1 from information_schema.columns
          where table_schema = 'public' and table_name = 'menu_items' and column_name = 'stock_qty') as m0062_stock,
  exists (select 1 from information_schema.columns
          where table_schema = 'public' and table_name = 'order_items' and column_name = 'options') as m0062_line_options,
  exists (select 1 from information_schema.columns
          where table_schema = 'public' and table_name = 'orders' and column_name = 'invoice_no') as m0063_invoice_no,
  exists (select 1 from pg_trigger where tgname = 'orders_zz_assign_invoice')              as m0063_trigger,
  exists (select 1 from information_schema.columns
          where table_schema = 'public' and table_name = 'coupons' and column_name = 'starts_at') as m0064_offer_start,
  to_regclass('public.marketing_requests')  is not null as m0064_marketing,
  to_regclass('public.support_tickets')     is not null as m0064_support,
  to_regclass('public.user_notifications')  is not null as m0064_inbox,
  to_regclass('public.announcements')       is not null as m0064_announcements,
  exists (select 1 from storage.buckets where id = 'support-attachments')               as m0064_bucket;
    0064 creates support_tickets/support_messages with if not exists, in the same shape the Rider and Manager branches use, so whichever of those lands first creates them and the others converge.
  2. Merge and deploy the website Merge feat/vendor-app into master, push to both remotes, and deploy as usual. The app calls the new /api/vendor/* routes (store, menu, payments, reports, offers, reviews, marketing, support, notifications, invoice profile). The live site doesn't have them yet. The customer-side changes (variants and add-ons in the item sheet, the "shop closed" message, offers that start later) ship in the same deploy.
  3. Sign the release APK with the existing keystore Create apps/vendor/android/key.properties. It's gitignored, so never commit it: 
    storeFile=F:/secure/deligro-release.jks
storePassword=…
keyAlias=vendor
keyPassword=…
    It has to be the same deligro-release.jks and vendor alias the current Partner app was signed with, otherwise Android refuses the update. Then build: 
    cd apps/vendor
flutter build apk --release --dart-define-from-file=env/prod.json
    Confirm the signer is not "Android Debug": apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk. Version is 2.0.0+3. Version code 3 is above the installed app's 2 (mobile/roles.json).
  4. Optional: add the support phone number env/prod.json has no SUPPORT_PHONE, so Help & support hides its "Call Deligro" row and shows only tickets. To show it, add "SUPPORT_PHONE": "+91…" to env/prod.json before step 3's build. Push uses the OneSignal app ID that is already in env/prod.json. The server needs ONESIGNAL_REST_API_KEY, which the live site already has.
  5. Publish the update to shops Upload the signed APK where the site serves it, then in Admin → Settings, under the Partner app release fields, set the version code to 3, the download URL, and release notes. Set the minimum version to 3 only if you want to force the update. The app checks /api/app-version on launch and offers the download.

Owner test script

After steps 1–3, on a phone signed in as a real shop owner. Each line is one requirement area.

  1. Sign in with OTP. Sign out, then sign in with the password Deligro gave the shop. Pick the shop if you own more than one.
  2. Home: the figures match Reports → Sales report for "Today" and for all time.
  3. Place a test order from the customer app with a variant and an add-on. The phone rings. Accept it with a prep time, start preparing, mark it ready. The timeline shows each step.
  4. Open the delivered order: the invoice has an INV/2026-27/… number. Print the receipt and share the invoice.
  5. Store: close for 30 minutes. The customer site shows the shop as closed. Reopen it. Add a holiday for tomorrow.
  6. Products: set a dish's stock to 2 with a low-stock alert at 1; order it twice. The low-stock push arrives and the dish shows sold out.
  7. Offers: create a code that starts tomorrow. Checkout refuses it today with "That offer hasn't started yet."
  8. Payments: after an admin marks a settlement paid, the payout push arrives and the statement PDF lists its orders.
  9. Reports: export CSV, Excel and PDF for last month and open each one.
  10. Marketing: request a featured listing. Approve it in /admin/marketing; the push and the status update arrive.
  11. Support: raise a ticket with a photo. Reply from /admin/support and resolve it; both pushes arrive.
  12. Post an announcement in /admin/announcements. It appears in the app's inbox with an unread badge.

Known limits

  • "Both"-funded discounts (§9.6). Coupons are funded by either the shop or Deligro (funded_by is vendor or platform). The app shows which one, and the cost to earnings. A split-funded discount would need a schema and settlement change. It isn't in this release.
  • English only. The owner asked for no Hindi in the Partner app, so §16.8 is replaced. The website and the customer app still offer Hindi.
  • Search in past orders looks through the newest 1,000 orders in the chosen period. Narrow the period to search further back. Paging without a search has no limit.
  • Debug-signed test APK. See deployment step 3. Without the keystore, no build can update installed apps.
  • No staging database confirmed. The migrations were proven in an in-process Postgres and read paths were checked against the live database. Apply them to staging first if one exists.
  • Printing goes through Android's print service: Wi-Fi and Bluetooth printers with an Android print plugin, or save as PDF. Direct ESC/POS printing to thermal printers isn't included.
